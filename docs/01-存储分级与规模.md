# Clipflow · 存储分级与规模策略（v0.1）

> 本文回答：数据量涨到百万条 / 几十 GB 会不会崩？文件、视频、图片各自怎么存？加密怎么分级？
> **全部结论有实测支撑**，实验数据见 §5，脚本在 `bench/`。

---

## 1. 先纠正一个前提：剪贴板里到底装了什么

在本机（M4 Pro / macOS 27）实测 `NSPasteboard` 实际内容：

| 操作 | 剪贴板实际内容 | 大小 |
|---|---|---|
| Finder 复制一个 **200 MB 视频** | `public.file-url` = 一个路径字符串 | **76 B** |
| 复制一张 **3456×2234 截图** | `public.tiff`，**完全未压缩** | **235.64 MB** |

**结论一**：macOS 复制文件时**天生只给路径，文件内容根本不进剪贴板**。所以"几百兆的视频要不要复制进来 / 要不要加密"这个问题**不存在**——我们本来就只拿得到 76 字节。

**结论二**：真正的存储炸弹是**图片**，而且是最容易被忽略的那种。同一张图：

| 编码 | 大小 | 相对 TIFF |
|---|---|---|
| TIFF（剪贴板给的原始格式） | 235.64 MB | 100% |
| **PNG（无损）** | **12.45 MB** | **5.3%** |
| JPEG q0.9 | 3.43 MB | 1.5% |

→ **收到 `public.tiff` 立刻转 PNG 是本项目性价比最高的一条优化：无损，体积砍到 1/19。**
这比任何"多大以上用引用、多小以下用复制"的阈值策略重要一个数量级。

## 2. 规模压测：百万条会不会崩

10 万 → 100 万逐级压测（每级 10 万条，含 `idx_created` / `idx_app` 两个二级索引）：

| 规模 | 原始文本 | 库+索引 | 膨胀 | 写入吞吐 | 检索中位 | 检索最差 | 最大命中 | 带过滤 | 纯浏览 |
|---|---|---|---|---|---|---|---|---|---|
| 10 万 | 17.3 M | 53.6 M | 3.10x | 110,892 条/s | 0.14ms | 0.62ms | 20,000 | 0.18ms | 0.03ms |
| 50 万 | 86.8 M | 259.8 M | 2.99x | 70,392 条/s | 0.22ms | 0.47ms | 100,000 | 0.24ms | 0.02ms |
| **100 万** | **173.6 M** | **517.6 M** | **2.98x** | **59,502 条/s** | **0.27ms** | **1.46ms** | **200,000** | **0.31ms** | **0.03ms** |

跑一次 `INSERT INTO fts(fts) VALUES('optimize')`（耗时 2.7s）后：**检索中位 0.10ms / 最差 0.53ms**。

**结论**：
- 检索延迟**不随规模线性劣化**（10 倍数据量只慢 1.9 倍），符合 B-tree + 倒排索引的对数复杂度预期
- 16ms 预算下**余量 58 倍**
- 写入吞吐 6–11 万条/s，而剪贴板真实负载是每天几百条 —— 差 3 个数量级
- 膨胀比稳定在 **~3.0x**（文本 1.3x + FTS 索引 1.2x + 二级索引 0.5x）
- **100 万条文本 = 518 MB。所以"几十 GB"不可能来自文本，只可能来自图片。**

**运维动作**：空闲时（无用户交互 > 60s）跑 `FTS optimize` + `incremental_vacuum`，按条目增量计数触发（每新增 5 万条一次）。

## 3. 内容分级存储策略

按"剪贴板实际给了我们什么"分，而不是按用户直觉的文件类型分：

### T1 · 文件与文件夹（`public.file-url`）

剪贴板只给路径 → **默认只存引用**（几十字节）。

| 项 | 做法 |
|---|---|
| 存什么 | 路径 + 文件大小 + mtime + inode + volume UUID |
| 失效检测 | 每次展示前 `stat` 校验；文件被删/移动 → 条目标记为"原文件已不存在"，**不静默失败** |
| **保全模式**（可选，默认关） | 小于阈值（默认 **20 MB**）的文件复制一份进 blob 库，防原文件被删。大于阈值只存引用 |

> 引用的固有代价必须说清楚：**原文件被删除或移动，历史条目就成了死链**。这不是 bug，是"引用"这个选择本身的代价。所以给保全模式的开关，让用户自己权衡。

### T2 · 图片（`public.tiff` / `public.png` / …）

**图片没有源文件可引用**——截图、从浏览器复制的图，都是纯 bitmap，磁盘上不存在对应文件。所以必须存，问题只是"存多大"。

处理管道（按序）：

1. **转码**：TIFF → PNG（无损，5.3%）。这一步砍掉 19/20，**无条件执行**
2. **CAS 去重**：SHA-256 命名，同一张图复制 100 次只占一份
3. **超大图降级**：PNG 仍 > 阈值（默认 20 MB）→ 按"存储策略"档位决定转 HEIC/JPEG 还是原样留
4. **缩略图分离**：列表滚动只读缩略图（512px），永不解码原图
5. **分级保留**：超过 N 天的图片自动只留缩略图，释放原图（可关）

### T3 · 文本 / 富文本

- < 512 B：内联进 SQLite 行
- ≥ 512 B：LZFSE 压缩后外置 blob（富文本压到 ~40%，纯文本/代码压到 ~5%）
- 长文本**只索引前 4 KB**

## 4. 存储策略档位（替代"滑条"）

你提的"让用户拖动滑条选节约空间还是保留数据"方向对，但**抽象滑条的问题是用户不知道自己选了什么**。改成三个具名档位，每档把代价写明：

| 档位 | 图片 | 文件 | 保留期 | 100 万条 + 5000 张图的估算占用 |
|---|---|---|---|---|
| **省空间** | 转 JPEG q0.9（1.5%）+ 30 天后只留缩略图 | 只存引用 | 90 天 | ≈ 0.5 GB + 3.4 GB → **~4 GB** |
| **均衡**（默认） | 转 PNG 无损（5.3%）+ 180 天后只留缩略图 | 引用 + < 20MB 保全 | 365 天 | ≈ 0.5 GB + 12 GB → **~13 GB** |
| **保真** | PNG 无损永久保留 | 全部保全副本 | 永久 | 无上限，随使用增长 |

每档在设置界面**实时显示当前实际占用 + 按当前档位的预估增长率**，而不是让用户盲选。

## 5. 加密分级（修正 D4）

> 这里我修正上一版方案。上一版基于"加密拖慢搜索"的假设，实测后该假设的权重变了。

### 5.0 竞品实况（实测，非营销话术）

| 产品 | 本地库加密 | 证据 |
|---|---|---|
| **Paste**（$9.99/年，商业） | ❌ **明文 SQLite** | 本机实测：`db.sqlite` 61MB，文件头 `53514c69746520666f726d61742033` = `SQLite format 3`；外置附件为明文 `bplist`；**文件权限 644（同机任意用户可读）** |
| **Maccy**（19.3k★，MIT） | ❌ 无任何加密 | 源码 `grep -E "sqlcipher\|encrypt\|CryptoKit\|AES\|SecItem"` 结果为空 |
| **Raycast**（商业，闭源） | ✅ 声称加密并作为卖点 | [官方 Clipboard History 页](https://www.raycast.com/core-features/clipboard-history)：copied content "is encrypted on your local hard drive" |

> 市场是**分裂**的，不是"都不做"。且做的那家把它当卖点宣传。
> 另外记录两个 Paste 的观察（中立事实）：内置 **PostHog 遥测**（含 `replayBuffer` / `errorTracking` / feature flags），以及一个 **MCP server**（`mcp/clients.json`）。

**但"竞品做不做"不构成本项目的决策依据**，威胁模型才是 → §5.1a。

### 5.1a 威胁模型：加密到底防什么

| 威胁 | 加密是否有效 | 说明 |
|---|---|---|
| 主动运行的恶意软件 | ❌ **无效** | 它可直接轮询 `NSPasteboard`，零权限、无提示、无审计。库加不加密都绕不过 |
| **历史存量泄漏** | ✅ **有效，且这是核心价值** | 恶意软件到达时只能看见"从此刻起"的内容；未加密的库里躺着**过去一年复制过的一切**。**存量档案的价值远高于当前剪贴板** |
| 备份泄漏 | ✅ 有效 | Time Machine / 同步到云盘目录 / 误传 GitHub / 设备送修转卖 |
| 同机其他用户 | ✅ 有效 | Paste 的 644 权限直接暴露；我们必须用 600 |
| 其他 App 顺手读取 | ✅ 有效 | 非沙盒 App 读 `~/Library/Application Support` **不需任何权限、不弹窗、不留痕**；而 Keychain 密钥有 ACL，取用会被拒或弹窗 |
| 设备物理丢失 | ⚠️ FileVault 已覆盖 | 本机实测 `fdesetup status` = On。这是"不加密"最站得住的一半理由 |

### 5.1 两个实测事实

1. **加密不是体积问题**：SQLCipher 每 page 加 64 B 保留区 = **+1.6%**
2. **性能余量比预想大得多**：100 万条下检索中位 0.10–0.27ms、最差 1.46ms，**16ms 预算余量 58 倍**。即使全库加密让 page 读慢 5 倍，也只到 ~7ms，仍在预算内

### 5.2 分层结论（三级，不是全做也不是全不做）

| 级 | 项 | 决定 | 理由 |
|---|---|---|---|
| ① | **库文件权限 600** | **必做** | 零成本。Paste 用 644 是白送的错误（同机任意用户可读），没理由跟着犯 |
| ② | **blob 加密**（图片/文件副本/大文本）<br>AES-GCM + Keychain | **必做，默认开** | blob **不参与检索**，只在用户点开那一条时解密一次，12 MB 图硬件加速下约 10ms。**代价几乎为零**；而截图里恰恰是后台管理页/聊天记录/密码框，**图片往往比文本更敏感** |
| ③ | **SQLite 主库（含 FTS 索引）全加密** | **默认开、可关；M2 实测 SQLCipher 后定** | 有 58 倍余量，很可能负担得起；负担不起就退回 ② |

**产品层面的理由（比技术理由更重要）**：Raycast 说它加密，用户只能选择相信——它闭源。**本项目开源，说加密别人可以自己验证。** "本地加密 + 代码可审计"是相对闭源 Paste 的天然差异化叙事，且工作量很小（不是同步/后端那种量级）。

### 5.3 关于"图片是不是没必要加密"

**恰恰相反，图片是最该加密的。** 截图里经常是后台管理页、聊天记录、密码输入框、证件照——**截图往往比文本更敏感**。而且如 §5.2，加密 blob 的代价几乎为零。所以默认加密图片，不给关闭理由。

### 5.4 必须诚实说明的一点

`detail=full` 的 FTS5 索引**存储了词元及其位置**，这意味着**索引本身在相当程度上可以还原原文**。所以：

- "主库不加密、只加密内容" 对**文本**而言是**自欺欺人**——索引还在那儿
- 对 **blob（图片/文件）** 则是真实有效的，因为图片二进制从不进索引

→ 所以要么全库加密（连索引一起），要么就诚实告知用户"文本历史的机密性等同于文件权限 + FileVault"。**不能两头都想要还宣称安全。**

### 5.5 M2 决策闸门

在 M2 阶段用真实 SQLCipher 做基准测试，判据：

- **通过**（100 万条下 P95 < 8ms）→ **全库加密设为默认**，附"高性能模式"开关允许关闭
- **不通过** → 退回分层方案：blob 加密 + 敏感条目单独加密不入索引 + 主库明文，并在 README 显著位置说明机密性边界

> 当前状态：**未实测 SQLCipher，上述 5 倍开销是外推估计，不是结论。** M2 前不得据此宣称"已支持全库加密"。

| 历史保留期 | 365 天 | 按档位联动 |

## 6a. 竞品实证带来的两处设计变更（源自 [02-Paste底层实现分析.md](./02-Paste底层实现分析.md)）

### 变更一：索引库与内容库分离（抄 Paste）

Paste 用**两个数据库文件**：`db.sqlite`（Core Data 内容）+ `index.sqlite`（FTS5 + spellfix1 + OCR）。本机核实其 `index.sqlite` schema：

```
items_fts   VIRTUAL TABLE USING fts5(app,type,title,content,device, content=items, ...)   -- external content
vocabulary  VIRTUAL TABLE USING spellfix1                                                  -- 拼写容错
items_vocab VIRTUAL TABLE USING fts5vocab('items_fts','row')
items_ocr / ocr_queue / fts_queue                                                          -- OCR 与索引异步管道
triggers: items_ai / items_au / items_ad                                                   -- 外部内容同步
```

**采纳**：Clipflow 同样拆成 `clipflow.sqlite`（内容）+ `clipflow-index.sqlite`（FTS5）。收益：
- 索引可整体删除重建而不动内容一个字节（改分词策略、修索引损坏时极重要）
- 两库可分别调 `page_size` / `cache_size`（索引库随机小读，内容库顺序大读，最优参数不同）
- 加密策略可分离：内容库加密、索引库单独处理，不必一刀切

> 注：`spellfix1` 对中文基本无效（它按编辑距离做拉丁词纠错），我们的 **bigram 分词**才是中文检索的关键。spellfix1 可作为英文/代码标识符的补充，优先级低。

### 变更二：图片 OCR —— 我们原方案的空白，补进路线图

Paste 用 Vision 框架对图片做 OCR 并入全文索引，**使截图里的文字可被搜索**。对剪贴板管理器这是高价值功能（"我截过一张图，里面有那个 IP"），而 `VNRecognizeTextRequest` 本地运行、零第三方依赖、零成本。

**采纳**：作为 Ingest 管道的一个可插拔 Processor（`OCRProcessor`），**异步执行不阻塞入库**（照抄 Paste 的 `ocr_queue` 队列模式）。默认开启，可关（OCR 耗电，笔记本电池模式下自动降级）。排进 **M4**。

### 反面教材：Paste 的存储浪费（实测数据）

| 项 | 实测 |
|---|---|
| 外置附件总量 | 506 个文件 / **708 MB** |
| 其中含 `public.tiff` 的 | **49 个（9.7%）→ 346 MB（占总量 49%）**，平均 7.0 MB/个 |
| 结论 | **一半存储浪费在 10% 的条目上，且是纯无损可省的**（转 PNG 只需 5.3%）→ §1 的转码决策收益实锤 |

另：Paste 的外置阈值实测为 **128 KiB**（非 Core Data 默认的 1 MB），导致主库塞入大量预览 blob。→ 佐证 Clipflow 选 **512 B** 阈值是对的。
