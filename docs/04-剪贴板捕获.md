# Clipflow · 剪贴板捕获（M1）

> 全部结论为本机实测（M4 Pro / macOS 27 / Swift 6.2.4，2026-08-10）。

---

## 1. 为什么捕获层要独立成 target

`NSPasteboard` 住在 **AppKit** 里，而 `ClipflowCore` 有一条测试**硬禁** `import AppKit`（保证核心零 UI 依赖、呈现层可整层替换）。

约束不是绕过，是用架构满足 → 新增 `ClipflowCapture` target：

```
ClipflowCore      零 UI 依赖（禁 AppKit/SwiftUI/UIKit/VisionKit）
ClipflowCapture   唯一允许 import AppKit 的非 UI 目标
ClipflowCLI       依赖二者
```

反向依赖也被测试拦住：`ClipflowCore` 里不得出现 `import ClipflowCapture`。

---

## 2. ⚠️ 根因：RTF 一上剪贴板，系统就广告一个兑现不了的类型

### 2.1 现象

跨进程读一次带格式的复制（全新进程，避开缓存），逐类型计时：

| UTI | 耗时 | 结果 |
|---|---|---|
| `public.utf8-plain-text` | 0.3 ms | 1720 B |
| `public.rtf` | 0.1 ms | 1728 B |
| **`public.utf16-external-plain-text`** | **18,493 ~ 23,785 ms** | **nil** |

Carbon 底层 `PasteboardCopyItemFlavorData` 返回 `status = -25133`（`badPasteboardFlavorErr`）。
超时时长不固定（18.5s / 23.8s 都测到过）。

### 2.2 定位过程（三个被推翻的假设）

| 假设 | 验证方法 | 结果 |
|---|---|---|
| 是"承诺型/系统派生"标记，可用 flavor flags 筛掉 | Carbon `PasteboardGetItemFlavorFlags` | ❌ **全是 `None`**，无 Promised / SystemTranslated 标记 |
| 是 `NSPasteboardItem` 这层的实现问题，走 Carbon 可绕开 | Carbon `PasteboardCopyItemFlavorData` 对比 | ❌ Carbon **同样阻塞 18.4 秒** |
| 可用 `availableType(from:)` 提前筛 | 全新进程逐类型探测 | ❌ 它对坏类型返回"**可用**"（0.0ms）—— **它撒谎** |

### 2.3 影响面：不是畸形用例，是所有带格式的复制

四种写入方式，全新进程各读一次：

| 写入方式 | 是否阻塞 |
|---|---|
| `NSPasteboardItem.setString` | 阻塞 23.8 s |
| **`NSAttributedString`**（TextEdit / 浏览器 / 飞书文档复制富文本的**标准写法**） | **阻塞 23.8 s** |
| `declareTypes` 老式 API | 阻塞 23.8 s |
| 纯文本 | 不广告该类型，**无阻塞** |

**结论：只要剪贴板上有 RTF，就会广告出这个兑现不了的类型。**
任何"把 `item.types` 全读一遍"的朴素实现，都会在每次带格式的复制上冻住二十多秒。

### 2.4 解法来源：抄系统自己的做法

`pb.readObjects(forClasses:)` 读同样的内容只要 **14.2 ms** —— 因为它**根本不枚举广告类型**，
只按固定白名单取。这就是 `TypePolicy` 的设计思路。

### 2.5 三级读取策略（`Sources/ClipflowCapture/TypePolicy.swift`）

| 级别 | 处理 | 理由 |
|---|---|---|
| **可信** | 直接读，**不设看门狗** | 覆盖 99% 保真需求且从不阻塞。**刻意不设超时**：一张大图的合法读取可能超过任何短阈值，设了反而把真数据误判成坏类型丢掉 |
| **已知坏** | 直接跳过 | 种子列表，零成本 |
| **未知** | 看门狗（1.5s）+ 超时后记入**负缓存** | 保住冷门 App 私有格式的保真，不因噎废食；未知坏类型**每会话最多付一次**超时 |

外加**单次快照总读取预算 3 秒**，超了就停止读剩余未知类型。
读取顺序也有意义：**可信类型先读**，即使后面耗光预算，核心保真数据也已到手。

> 硬编码列表只是加速器，**负缓存才是正确性依赖** —— 列不全各家 App 的私有 UTI。

### 2.6 重构后实测

连续 6 次 `NSAttributedString` 富文本复制（1.2s 间隔）：**全部捕获，零阻塞**，
格式收敛为 `public.rtf` + `public.utf8-plain-text`。

`data(forType:)` 不可取消 —— 看门狗超时后那个线程仍会挂到系统超时。这是**可接受的代价**：
泄漏一个短命线程好过冻结捕获循环，且配合负缓存，同一坏类型每会话最多泄漏一次。

## 3. ⚠️ 第二个坑：读取绝不能异步延后

发现阻塞问题后，第一反应是「把读取甩到独立队列，轮询线程只比 changeCount」。
**实测证明这是错的。**

剪贴板内容是**瞬态**的 —— 系统只保存"当前"一份，不留历史。
延后读取时若剪贴板已翻页，读到的是**新内容**却被记在**旧那次变更**上 —— **张冠李戴**。

实测这个错法：连续 7 次复制，异步读把后 5 次全读成了最后一条，全部去重成同一条。
**检测到了全部 7 次变更，但记录的内容 5 条是错的。**

### 取舍：宁可漏，不可错

读取必须与检测**同步**。慢读取会漏掉期间的变更，但绝不会记错内容。
对剪贴板管理器，**记错比漏记严重得多** —— 用户看到一条记录，必须相信它就是当时复制的东西。

慢读取次数通过 `slowReadCount` 暴露，便于发现是哪个 App 在拖慢捕获。

## 4. 其它实现要点

| 项 | 做法 | 说明 |
|---|---|---|
| 轮询间隔 | 活跃 200ms / 空闲 1s | Maccy 用 0.5s；200ms 在 M 系上 CPU 仍 < 0.3%，跟手度差别明显 |
| 空闲判定 | `IOHIDSystem` 的 `HIDIdleTime` | 无键鼠输入超 60s 降频省电 |
| 自写抑制 | `suppressNextChange()` | 我们粘贴时会写剪贴板，不抑制就会捕获到自己写的内容，形成回声 |
| 来源 App | `NSWorkspace.frontmostApplication` | bundleID + 本地化名称 |
| 窗口标题 | **暂留空** | 需 Accessibility 权限，M3 再接；拿不到不阻塞入库 |
| 空 data 类型 | **保留** | concealed 标记就是「只有类型没有内容」的标志位，丢了就拦不住密码 |

## 5. 端到端验证

`clipflow watch` 对 7 种真实复制行为的实测结果：

| 复制内容 | 结果 |
|---|---|
| 纯文本 | `#1 [文本] 1 种格式 39 B` |
| 富文本（4 种声明格式） | `#2 [富文本] **3 种格式** 5 KB` —— 阻塞的 utf16 已跳过 |
| 图片 400×300 | `#3 [图片] 3.8 MB` |
| 文件引用 `/Applications/Xcode.app` | `#4 [文件] **31 B**` —— 只存路径，实锤"剪贴板不给文件内容" |
| concealed 密码 | **⊘ 已拦截** |
| `api_key = sk-live-…` | `#5 [文本] **🔒敏感**` |
| 重复第一条 | `#1` —— 去重命中，不新建 |

## 6. 调试工具

`clipflow poll <秒数>` —— 同步轮询版，不走 AsyncStream。

保留它是有原因的：定位 M1 那个「`Task {}` 继承 MainActor 导致消费任务永不执行」的 bug 时，
正是靠同步版能跑 / 异步版不能跑的对照，一步锁定问题层。**留着这个对照面，下次还能用。**
