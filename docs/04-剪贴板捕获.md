# Clipflow · 剪贴板捕获（M1）

> 全部结论为本机实测（M4 Pro / macOS 27 / Swift 6.2.4，2026-08-10）。

---

## 1. 为什么捕获层要独立成 target

`NSPasteboard` 住在 **AppKit** 里，而 `ClipflowCore` 有一条测试**硬禁** `import AppKit`（保证核心零 UI 依赖、呈现层可整层替换）。

约束不是绕过，是用架构满足 → 新增 `ClipflowCapture` target：

```
ClipflowCore      零 UI 依赖（禁 AppKit/SwiftUI/UIKit/VisionKit）
ClipflowCapture   唯一允许 import AppKit 的非 UI 目标
ClipflowCLI       依赖二者
```

反向依赖也被测试拦住：`ClipflowCore` 里不得出现 `import ClipflowCapture`。

## 2. ⚠️ 一次被推翻的"根因"（保留全过程，教训比结论值钱）

### 2.1 观察到的现象

跨进程读一次带格式的复制，逐类型计时：

| UTI | 耗时 | 结果 |
|---|---|---|
| `public.utf8-plain-text` | 0.3 ms | 1720 B |
| `public.rtf` | 0.1 ms | 1728 B |
| **`public.utf16-external-plain-text`** | **18,493 ~ 28,536 ms** | **nil** |

Carbon 层可见 `status = -25133`（`badPasteboardFlavorErr`）。当时的结论是：
**「只要剪贴板上有 RTF，macOS 就会广告一个兑现不了的类型」** —— 并据此把它列入黑名单跳过。

### 2.2 这个结论是错的

决定性对照实验 —— 只改**写入进程的形态**，其余全部相同：

| 写入进程 | 读 `utf16-external` |
|---|---|
| `Thread.sleep`（run loop 不转，早期测试写法） | **28,536 ms → nil** |
| `RunLoop.run()`（**真实 App 的形态**） | **0.2 ms → 1522 B** ✅ |

该类型是 **lazy promise**，由拥有者进程**通过 run loop** 兑现。
早期测试的写入进程只 `Thread.sleep`、run loop 是死的，承诺永远无人兑现，于是一路等到系统超时。

**真实 App 都在跑 run loop，所以真实场景根本没有这个问题。**

### 2.3 竞品旁证

Maccy（19.3k★）的读取循环（`Maccy/Clipboard.swift`）：

```swift
types = types
  .subtracting(disabledTypes)
  .filter { !$0.rawValue.starts(with: dynamicTypePrefix) }
  .filter { !$0.rawValue.starts(with: microsoftSourcePrefix) }
types.forEach { type in
  contents.append(HistoryItemContent(type: type.rawValue, value: item.data(forType: type)))
}
```

**读所有类型，无任何超时保护**，且从无"富文本复制卡顿"的用户报告 —— 与"真实场景无此问题"相互印证。

### 2.4 教训

> **跨进程行为的测试，对端必须模拟真实进程形态。**
> 用一个不跑 run loop 的进程当写入方，测出来的是脚手架的病，不是被测对象的病。

这次的代价是：基于错误结论做了一轮捕获层重构，并把一个**含真数据的合法类型**（实测 1522 B）
列入黑名单跳过 —— 造成了真实的**保真度倒退**。已回退，并留下回归测试守着不许再犯。

### 2.5 修正后的策略

主路径**读所有类型**（与 Maccy 一致，保真优先），只做两件事：

| 措施 | 依据 |
|---|---|
| 过滤 `dyn.*` 动态类型 | 系统给未注册 UTI 生成的临时标识，无稳定语义 |
| 过滤 Word 链接源（`com.microsoft.linksource` / `objectlink` / `ole.source`） | Maccy #613 / #770，真实 issue |
| 保留 2s 看门狗 + 负缓存 | **不是**为那个被证伪的缺陷，而是兜住"拥有者进程真的退出/挂死"的边缘情况 |

看门狗阈值取 2s 而非更短：**大图的合法读取可能要几百毫秒，阈值太短会把真数据误判丢掉**。
正常情况下所有类型都是毫秒级，这条路径根本不会触发 —— `NegativeTypeCache.learned`
长期非空说明环境异常，该排查而不是默默容忍。

### 2.6 修正后实测

真实 App 形态的写入方（跑 run loop），捕获结果：

```
#1 [富文本] 3 种格式 8 KB
  public.rtf                        5 KB   lzfse
  public.utf16-external-plain-text  2 KB   lzfse   ← 真数据，已恢复保留
  public.utf8-plain-text            2 KB   lzfse
```

## 3. ⚠️ 第二个坑：读取绝不能异步延后

发现阻塞问题后，第一反应是「把读取甩到独立队列，轮询线程只比 changeCount」。
**实测证明这是错的。**

剪贴板内容是**瞬态**的 —— 系统只保存"当前"一份，不留历史。
延后读取时若剪贴板已翻页，读到的是**新内容**却被记在**旧那次变更**上 —— **张冠李戴**。

实测这个错法：连续 7 次复制，异步读把后 5 次全读成了最后一条，全部去重成同一条。
**检测到了全部 7 次变更，但记录的内容 5 条是错的。**

### 取舍：宁可漏，不可错

读取必须与检测**同步**。慢读取会漏掉期间的变更，但绝不会记错内容。
对剪贴板管理器，**记错比漏记严重得多** —— 用户看到一条记录，必须相信它就是当时复制的东西。

慢读取次数通过 `slowReadCount` 暴露，便于发现是哪个 App 在拖慢捕获。

## 4. 其它实现要点

| 项 | 做法 | 说明 |
|---|---|---|
| 轮询间隔 | 活跃 200ms / 空闲 1s | Maccy 用 0.5s；200ms 在 M 系上 CPU 仍 < 0.3%，跟手度差别明显 |
| 空闲判定 | `IOHIDSystem` 的 `HIDIdleTime` | 无键鼠输入超 60s 降频省电 |
| 自写抑制 | `suppressNextChange()` | 我们粘贴时会写剪贴板，不抑制就会捕获到自己写的内容，形成回声 |
| 来源 App | `NSWorkspace.frontmostApplication` | bundleID + 本地化名称 |
| 窗口标题 | **暂留空** | 需 Accessibility 权限，M3 再接；拿不到不阻塞入库 |
| 空 data 类型 | **保留** | concealed 标记就是「只有类型没有内容」的标志位，丢了就拦不住密码 |

## 5. 端到端验证

`clipflow watch` 对 7 种真实复制行为的实测结果：

| 复制内容 | 结果 |
|---|---|
| 纯文本 | `#1 [文本] 1 种格式 39 B` |

| 图片 400×300 | `#3 [图片] 3.8 MB` |
| 文件引用 `/Applications/Xcode.app` | `#4 [文件] **31 B**` —— 只存路径，实锤"剪贴板不给文件内容" |
| concealed 密码 | **⊘ 已拦截** |
| `api_key = sk-live-…` | `#5 [文本] **🔒敏感**` |
| 重复第一条 | `#1` —— 去重命中，不新建 |

正是靠同步版能跑 / 异步版不能跑的对照，一步锁定问题层。**留着这个对照面，下次还能用。**
