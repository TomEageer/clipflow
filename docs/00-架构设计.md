# Clipflow 架构设计（v0.1 草案）

> 工作代号 **Clipflow**，正式名待定。
> 场景分流：**S3 计划功能开发**（新项目）。本文档 = 技术方案阶段产出，未拍板项见 §8。
> 目标定位：**开源 + 商业级质量**的 macOS 剪贴板管理器。架构自由度 / 性能 / 拓展性优先，UI 后置。

## 1. 调研结论：为什么从零写

### 1.1 现有开源方案实测

| 项目 | 栈 | 许可证 | 结论 |
|---|---|---|---|
| [Maccy](https://github.com/p0deje/Maccy) 19.3k★ | Swift + AppKit + SwiftData | MIT | **当踩坑答案册读，不 fork** |
| [PasteBar](https://github.com/PasteBar/PasteBarApp) 2.1k★ | Tauri(Rust) + React 19 | CC BY-NC（非 OSI，商用受限） | 功能最全但许可证挡死商用，WebView 非原生 |
| Flycut | Obj-C | MIT | 只做纯文本，已老化，仅参考 |
| CopyQ | Qt | GPL | 跨平台，Mac 上观感割裂 |

### 1.2 Maccy 已有、不构成差异化的功能（源码实证）

- `Maccy/PopupPosition.swift` — 已支持 `.cursor` 鼠标旁弹出（且是默认 fallback 分支），含跨屏边界钳制 `constrained(_:ofSize:to:)`
- `Maccy/PasteStack.swift` — 已有粘贴栈：全局 `NSEvent` 监听 Cmd+V 的 keyUp，按修饰键多选后依次吐出
- 已尊重 concealed 标记（1Password/Bitwarden 密码不入库）
- 已有 46 种语言本地化、Sparkle 自动更新、App Store 上架

### 1.3 Maccy 的三处架构天花板（正对我们的性能目标）

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| A1 | `Storage.swift` — `@MainActor class Storage`，`var context: ModelContext { container.mainContext }` | 所有 DB 操作绑主线程 | 写入/查询与 UI 争抢主线程，大库时掉帧 |
| A2 | `Models/HistoryItemContent.swift` — `var value: Data?` | 图片/RTF blob 直存 SQLite 行内 | 几千张截图后库膨胀到 GB 级，无外置策略、无内容去重 |
| A3 | `Search.swift` — `search(string:within: [Searchable])` 内存遍历 + Fuse 模糊匹配，`fuzzySearchLimit = 5_000` | **零索引**，线性扫描 | 条目数上去必然劣化，只能靠截断掩盖 |

**结论**：Maccy 的架构是为"轻量、文本优先、几千条"设计的，与本项目"十万条含图、输入即搜、可插拔"的目标结构性冲突。Fork = 继承 A1/A2/A3。

## 2. 架构总览

设计主轴：**核心与呈现彻底解耦**。呈现层（鼠标旁浮窗 / 菜单栏 / 全屏面板 / 未来任何形态）只是 Core 的一个消费者，可以整层替换而不动核心。

```
┌─────────────────────────────────────────────────────────┐
│  Shell 层（可整层替换 · 多实现并存）                        │
│  CursorPanelShell │ MenuBarShell │ FullScreenShell │ CLI  │
└───────────────────────┬─────────────────────────────────┘
                        │ 只依赖 ClipflowCore 的协议
┌───────────────────────▼─────────────────────────────────┐
│  ClipflowCore（纯 Swift Package · 零 UI 依赖 · 可单测）    │
│                                                          │
│  ┌────────────┐  ┌──────────────┐  ┌─────────────────┐  │
│  │ Capture    │→ │ Ingest 管道   │→ │ Store           │  │
│  │ 轮询/来源   │  │ 可插拔处理器链 │  │ SQLite+FTS5+CAS │  │
│  └────────────┘  └──────────────┘  └────────┬────────┘  │
│                                              │           │
│  ┌────────────┐  ┌──────────────┐  ┌────────▼────────┐  │
│  │ Paste 引擎  │← │ Transform    │← │ Query           │  │
│  │ 焦点/合成键 │  │ 可插拔变换链  │  │ 索引检索/过滤    │  │
│  └────────────┘  └──────────────┘  └─────────────────┘  │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │ Extension Host — 外部脚本契约（stdin/stdout JSON）│   │
│  └──────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

**Package 切分**（一开始就分，后面再拆代价大）：

- `ClipflowCore` — 捕获/存储/查询/变换/粘贴，零 UI import，100% 可单测
- `ClipflowUI` — 共享视图组件与 ViewModel
- `Clipflow` — App target，负责装配 Shell + 权限 + 生命周期
- `clipflow-cli` — 命令行客户端，**同时是"核心真的解耦了"的强制验证**（CLI 跑得通 = Core 没偷偷依赖 UI）

## 3. 分层设计

### 3.1 Capture 层

macOS **没有剪贴板变更通知**（无 NSNotification / 无 KVO / 无回调），只能轮询 `NSPasteboard.general.changeCount`。

```swift
protocol ClipSource: Sendable {
    var events: AsyncStream<RawSnapshot> { get }
}
```

- `LocalPasteboardSource` — 轮询实现，默认 200ms（Maccy 用 0.5s；200ms 在 M 系上 CPU 仍 <0.3%，交互跟手度差别明显）
- **自适应节流**：前台有输入活动时 200ms，系统 idle > 60s 降到 1s，省电
- 抽象成协议是为了未来接 `NetworkSource`（跨设备同步）、`iOSSource` 而不动下游

**必须踩的坑（Maccy 已解，抄）**：
- **Lazy pasteboard provider** — 部分 App 只在被读取时才生成内容，读取时机错了拿到空。必须在 changeCount 变更后立即读全 `pasteboardItems`
- 自己写回剪贴板会触发自己的轮询 → 必须记录 self-write 的 changeCount 做抑制
- 一次复制 = 一个 `NSPasteboardItem` 挂多个 representation，**必须全量捕获**，不能只取字符串

### 3.2 Ingest 管道（拓展点 ①）

```swift
protocol IngestProcessor: Sendable {
    var identifier: String { get }
    func process(_ ctx: inout IngestContext) async throws -> IngestDecision  // .continue / .drop(reason)
}
```

内置处理器（按序）：

1. `ConcealedFilter` — 尊重 `org.nspasteboard.ConcealedType` / `com.agilebits.onepassword` / `Pasteboard generator type`，密码类直接丢弃
2. `SourceAppFilter` — 来源 App 黑白名单（按 bundle ID）
3. `SizeGuard` — 单条上限（默认 50MB），超限降级只存元数据
4. `Deduplicator` — 内容 SHA-256 去重，命中则只更新 `lastUsedAt` 不新建行
5. `TypeClassifier` — 识别 URL / 颜色 / 邮箱 / JSON / SQL / 代码 / 图片 / 文件 / 富文本
6. `ContextEnricher` — 来源 App bundle ID + 图标 + 窗口标题 +（浏览器时）当前页 URL

> **窗口标题需要 Accessibility 权限**，沙盒下受限 → 关联 D3 决策。此处设计为**可降级**：拿不到就留空，不阻塞主链路。

### 3.3 Store 层（关键决策 D1）

**不用 SwiftData / Core Data，用 GRDB + SQLite。**

理由（直接对应 Maccy 的 A1/A2/A3）：
- SwiftData 的 `ModelContext` 强绑 actor，后台写入模式受限 → 我们要 writer 独占串行队列 + reader 池，与 UI 线程完全隔离
- SwiftData 无 FTS5 接入路径 → 我们要真索引，不要内存遍历
- blob 策略需要自己掌控 → SwiftData 做不到外置 CAS
- 迁移可控性：商业产品的库结构一定会改，GRDB 的 `DatabaseMigrator` 是显式可测的，SwiftData 的自动迁移在复杂 schema 上不可控

**存储布局**：

```
~/Library/Application Support/Clipflow/          # 全目录权限 700，库文件 600
├── clipflow.sqlite          # 内容库：元数据 + 小文本内联
├── clipflow-index.sqlite    # 索引库：FTS5（可整体重建，与内容库分离）
├── blobs/                   # 内容寻址存储 CAS，SHA-256 两级分桶
│   ├── a3/f2/a3f2....png     # 天然去重：同一张图复制 100 次只存一份
│   └── ...
└── thumbs/                  # 预生成缩略图（列表滚动不解码原图）
```

> **索引库独立成文件**是从 Paste 实证中抄来的（它拆成 `db.sqlite` + `index.sqlite`）。收益：索引可整体删除重建而不动内容、两库可分别调 `page_size`/`cache_size`、加密策略可分离。详见 [01 §6a](./01-存储分级与规模.md)。

表设计要点：
- `items` — id / createdAt / lastUsedAt / sourceBundleID / windowTitle / kind / pinned / collectionID / contentHash
- `representations` — itemID / uti / inlineValue(小于 512B 内联) / blobHash(大于则外置) / codec(none|lzfse)
- `items_fts` — FTS5 **contentless**（`content=''`）虚表，只建索引不重复存原文，按 rowid 回 `items` 取内容
- **中文分词**：FTS5 默认 tokenizer 对中文无效 → 应用层做 **bigram 分词**后写入索引（不引第三方，约 30 行，SQL 注入面为零）

**以下四条由实测定（数据见附录 A，10 万条 / 17.67MB 语料）**：

| 决策 | 结论 | 实测依据 |
|---|---|---|
| FTS5 `detail` 模式 | **`detail=full`** | `column` / `none` **根本不支持短语查询**（实测报错）。中文 bigram 检索"订单支付"必须要求 `订单/单支/支付` **连续出现**，否则退化成 AND 匹配、精度崩掉。代价是索引 123% vs 42%，认了 |
| 排序方式 | **永不 `ORDER BY rank`，一律 `ORDER BY id DESC`** | rank 必须给**每一条**命中打分：2 万条命中 → **46ms**；改 rowid DESC → **0.30ms**，快 **150 倍**。且剪贴板用户要的本来就是"最近的"不是"最相关的"——**更快且语义更对** |
| 压缩 | LZFSE（Apple 系统自带，零依赖），**阈值 512B，小于不压** | 富文本压到 ~40%，中文/代码/JSON 压到 ~5%；但 120B 短文本压完 117B（97.5%）纯属白费 CPU |
| 空间回收 | `PRAGMA auto_vacuum=INCREMENTAL` + 空闲时 `incremental_vacuum` | 删条目后 SQLite 默认不还盘 |

**并发模型**（Swift 6 严格并发）：
```swift
actor StoreActor {           // 单写者串行队列
    private let dbPool: DatabasePool   // GRDB WAL 模式，多读者并发
}
```
UI 通过 `ValueObservation` 拿变更流，**永不在主线程碰 DB**。

### 3.4 Query 层

- 短查询（< 3 字符）走前缀索引，长查询走 FTS5 短语查询
- **两级返回**：先返 20 条首屏（目标 < 8ms），后台补全剩余，UI 渐进填充
- 过滤维度：类型 / 来源 App / 时间范围 / 集合 / pinned，全部走索引列不做内存过滤
- ⚠️ **`ORDER BY rank` 列入代码禁令**（加 lint 规则拦截）。理由见 §3.3 表格：高频词场景下它是 46ms vs 0.30ms 的差距，是本项目最容易踩且最贵的性能陷阱
- **长文本只索引前 4KB**。一条 50KB 的日志粘贴，索引开头足够检索到它；全量索引换不来检索收益，只换来索引膨胀

### 3.5 Transform 层（拓展点 ②）

```swift
protocol Transformer: Sendable {
    var identifier: String { get }
    func canApply(to item: ClipItem) -> Bool
    func transform(_ item: ClipItem) async throws -> [PasteRepresentation]
}
```

内置：转纯文本 / 去多余空行 / URL 编解码 / JSON 格式化 / Base64 / 转 Markdown 表格 / 大小写转换。

**差异化核心（全市场空白）——`PasteProfileLearner`**：
按 `(源 App bundle ID, 目标 App bundle ID)` 二元组学习默认粘贴格式。从 Chrome 粘到 IDEA 手动转了两次纯文本，第三次自动转；粘到飞书文档保留富文本。这条是产品护城河，架构上必须在 Transform 层留出 profile 查询钩子。

### 3.6 Paste 引擎

粘贴序列（顺序错了就失败，Maccy 的实现值得逐行读）：
1. 关闭/隐藏自身面板 → **等待前台 App 真正恢复 key 状态**（不是固定 sleep，是轮询 `NSWorkspace.frontmostApplication`）
2. 备份当前剪贴板 → 写入目标内容
3. `CGEvent` 合成 Cmd+V（需 **Accessibility 权限**）
4. 延迟恢复原剪贴板（可配置，默认恢复）

**必须处理的失败面**：
- **Secure Input** — 密码框聚焦时系统吞掉合成事件。必须检测 `IsSecureEventInputEnabled()` 并给出明确提示，而不是静默失败
- 个别 App 不吃合成事件 → 降级为"已放入剪贴板，请手动 Cmd+V"
- 无 Accessibility 权限 → 全功能降级路径，不能崩

### 3.7 Shell 层

```swift
protocol ClipflowShell {
    func present(anchor: PresentationAnchor) // .cursor / .statusItem / .screenCenter / .frontmostWindow
    func dismiss()
}
```
- **预热常驻 `NSPanel`**（`.nonactivatingPanel`），热键触发时只做定位+显示，不现场构建视图 → 这是"热键到可见 < 100ms"的唯一可行路径
- 多屏边界钳制、Stage Manager、全屏 Space 兼容需实测

### 3.8 Extension Host（拓展点 ③ · 商业产品的关键）

不自研插件 DSL，走 **Raycast/Alfred 式外部进程契约**：

```
清单：~/Library/Application Support/Clipflow/extensions/<name>/manifest.json
协议：stdin 收 JSON(item + context) → stdout 吐 JSON(结果/新 representation)
沙箱：独立进程 + 超时 kill + 无网络能力声明则断网
```

好处：第三方不用会 Swift、不用编译、不能崩主进程。你自己的 Java 场景特化（SQL 格式化、trackID 跳 ES 查询）**先作为官方扩展实现一遍**——这是对扩展契约最好的压力测试。

## 4. 性能预算（量化，写进 CI 断言）

| 指标 | 目标 | 依据 / 验证方式 |
|---|---|---|
| 空闲 CPU | < 0.3% | 1 小时采样均值 |
| 常驻内存 | < 80 MB（10 万条库） | 图片走磁盘不常驻 |
| 热键 → 面板可见 | < 100 ms（P95） | 预热常驻 NSPanel；signpost 埋点 |
| 搜索首字符 → 首屏 20 条 | **< 16 ms（P95，10 万条）** | 实测 `ORDER BY id DESC` 最差 0.43ms，**余量 37 倍**；但 `ORDER BY rank` 会到 46ms 直接击穿 |
| 复制 → 入库可见 | < 250 ms | 轮询 200ms + 入库；端到端测 |
| **文本膨胀比**（库+索引 / 原始文本） | **≤ 2.6x** | 实测 detail=full 下 2.50x（数据 1.27x + 索引 1.23x）。绝对值参考：10 万条 = 44MB |
| **富文本膨胀比**（三 representation） | **≤ 1.4x** | 实测未压缩 3.44x → LZFSE 压缩后 **1.27x**（比只存 plain 一份还小） |
| 图片存储 | 无重复副本，原图不重编码 | CAS SHA-256 去重验证 |

**这些数字必须在 M2 阶段就有基准测试并写进 CI 断言**，否则等功能堆完再优化就来不及了 —— 这正是 Maccy 现在的处境。

> 关于你担心的"1M 数据变成 2M、3M"：实测真凶**不是加密**（+1.6%），而是**一次复制被存成 plain + html + rtf 三份（3.44x）**。LZFSE 压缩后降到 1.27x，问题即解。至于文本库的 2.5x 膨胀，10 万条的绝对值只有 44MB —— 不值得为它牺牲检索精度。**真正会失控的是图片**，靠 CAS 去重 + 不重编码原图控制。

## 5. 安全模型

macOS 侧**没有任何剪贴板权限门禁**：不提示、不审计，任何运行中的 App 都能读 `NSPasteboard.general`。所以安全责任 100% 在我们：

1. **Concealed 标记必须尊重**（否则本 App = 明文密码记录器）
2. **分级自动过期**：识别为 token/密码类 → 60 秒销毁；截图 → 7 天；代码片段 → 永久。目前全市场都是"一刀切条数上限"，这是差异化点也是安全底线
3. **扩展进程默认无网络**，需在 manifest 显式声明并经用户授权
4. **永不上传任何剪贴板内容**，包括崩溃报告 —— 崩溃日志必须脱敏

### 5.1 加密方案（D4 · 已决：分级加密，弃全库加密）

**先破除一个错误直觉**：加密不是体积膨胀的原因。实测 SQLCipher 每 page 加 64B 保留区 = **+1.6% 体积**，可忽略。加密的真实代价在**延迟**（每次 page 读都要 AES 解密 + HMAC 校验），而我们已经因为 `detail=full` 承担了偏大的索引读放大，两者叠加会吃掉 16ms 搜索预算。

**更关键的一点**：全库加密在本场景里**安全收益被高估**了。FTS5 索引里存的就是内容的 bigram 分词，拼起来基本能还原原文——只要索引在，"元数据不加密、内容加密"是自欺欺人。而全库加密后，密钥必须在 App 运行期间常驻内存，任何以你账户身份运行的进程照样能从内存里捞。

所以采用**分级**：

| 分级 | 判定 | 存储 | 索引 |
|---|---|---|---|
| **敏感**（token/密码/密钥/信用卡/私钥） | 分类器识别 + concealed 标记 + 正则（JWT、AKIA、`-----BEGIN`、X-Auth-Signature 这类） | **AES-GCM 单独加密**，密钥存 Keychain（`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`） | **不入 FTS 索引**（索引=明文泄露），**60 秒 TTL 自动销毁** |
| **普通** | 其余全部 | 明文 + LZFSE（> 512B） | 全速索引 |

依据：**你真正怕泄露的是密码和 token，不是"我复制过一段 SQL"**。把安全预算花在真正敏感的那不到 1% 上，把性能预算完整留给 99%。敏感条目本来就该短命，也不需要被搜索——安全与性能在这里不冲突。

底座仍要求：库文件权限 600 + 依赖 FileVault + 文档明确告知用户"本 App 会记录你复制的一切"。

## 6. MVP 里程碑

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| **M0 骨架** | Package 切分 + GRDB schema + migrator + CI | `clipflow-cli` 能 list/search，证明 Core 零 UI 依赖 |
| **M1 捕获入库** | 轮询 + 全 representation 捕获 + CAS blob + 去重 + concealed 过滤 | 复制文本/图片/文件/富文本各 20 次，格式无损可还原 |
| **M2 检索** | FTS5 + bigram 中文分词 + 两级返回 | 10 万条造数据下 P95 < 16ms（基准测试断言） |
| **M3 粘贴闭环** | 热键 + 鼠标旁 NSPanel + 焦点恢复 + CGEvent 粘贴 + Secure Input 检测 | 20 个常用 App 逐个实测粘贴成功 |
| **M4 差异化** | Transform 链 + PasteProfileLearner + 分级过期 + **图片 OCR**（Vision，异步队列） | 源→目标格式学习实测生效；截图内文字可被搜到 |
| **M5 产品化** | 扩展契约 + 设置界面 + 签名公证 + 自动更新 | 能给别人装 |

M0–M3 = 能自用。M4 = 比 Paste 好用。M5 = 能卖。

## 7. 已决策项

| ID | 决策 | 结论 | 理由 |
|---|---|---|---|
| D1 | 存储引擎 | **GRDB + SQLite + FTS5(detail=full, contentless) + CAS blob**，弃 SwiftData | 后台并发写、真索引、blob 外置、迁移可控 —— 正对 Maccy 三处天花板 |
| D2 | 进程模型 | 单进程 + actor 隔离，不拆 daemon。**例外：OCR 拆独立 XPC service** | XPC 复杂度换不来足够收益；"UI 崩溃不丢历史"用即时落盘更廉价地达成。**OCR 例外的依据**：实测 Vision 使进程内存 +200MB 驻留不还，撞破「常驻 < 80MB」预算 → 见 [03 §2.3](./03-图片OCR设计.md) |
| **D3** | 分发路线 | **GitHub 开源自编译为主线**，暂不买 $99；架构留 App Store 降级位 | 沈约已拍板。**架构要求**：需完整权限的能力（窗口标题读取、外部扩展进程）必须封装成 `Capability` 协议，沙盒下可降级不可崩 |
| **D4** | 加密 | **blob 默认全加密**（代价近零）；**主库/索引是否加密 → M2 实测 SQLCipher 后定**。详见 [01-存储分级与规模.md §5](./01-存储分级与规模.md) | 百万条压测后余量达 58 倍，全库加密从"负担不起"变成"很可能负担得起"。**此项已修正上一版结论** |
| **D5** | 商业模式 | **先全开源（核心 MIT）**，**不做同步**，后续高级功能/UI 扩展再闭源 | 沈约已拍板。**Apple 通用剪贴板已把 iPhone 复制的内容送进 Mac 剪贴板，我们照常捕获即可，同步这块根本不用自己做** |
| D6 | 是否 fork Maccy | **不 fork，从零写；逐段精读其源码当答案册** | 见 §1.3；另：收费产品建在 19.3k★ MIT 项目 fork 上是品牌负债 |
| **D7** | 闭源层如何预留 | **不做特殊设计**，只需把三个注册表定义干净 | MIT 零传染性，随时可加闭源模块。真正要现在做对的是 `TransformerRegistry` / `ShellRegistry` / `ProcessorRegistry` —— 闭源模块只需 `register()` 挂上，不改核心一行 |

### D3 的架构落点：Capability 协议

```swift
protocol Capability {
    var isAvailable: Bool { get }        // 沙盒/权限缺失时为 false
    var degradedBehavior: Degradation { get }
}
// 例：WindowTitleCapability 不可用 → windowTitle 留空，不阻塞入库
// 例：SyntheticPasteCapability 不可用 → 降级为"已放入剪贴板，请手动 Cmd+V"
```
**任何能力缺失都必须有降级路径，不允许崩溃或静默失败。** 这是 App Store 版本能否成立的前提，现在留位比以后返工便宜得多。

## 8. 附录 A · 实测数据（2026-08-10）

环境：M4 Pro / 24GB / SQLite 3.53.4。语料：**10 万条**模拟真实剪贴板内容（中文段落 / Java 代码 / SQL / JSON / 混合），原始文本 **17.67 MB**。脚本见 `bench/`。

### A1 · FTS5 三种 detail 模式（contentless，中文 bigram）

| detail | 数据 | 索引 | 索引/原文 | 总计 | 膨胀 | 短语查询 | AND 查询延迟(中位/最差) |
|---|---|---|---|---|---|---|---|
| **full** | 22.41M | 21.80M | 123.4% | 44.21M | **2.50x** | **✅ 支持** | 0.53 / 132.47ms |
| column | 22.41M | 18.22M | 103.1% | 40.63M | 2.30x | ❌ 不支持 | 0.32 / 39.87ms |
| none | 22.41M | 7.45M | 42.2% | 29.87M | 1.69x | ❌ 不支持 | 0.28 / 35.76ms |

> `none` 省下 14MB 很诱人，但**中文 bigram 检索没有短语查询就等于没有精度**。选 `full`。

### A2 · 尾延迟归因（decisive）

同一批 10 万条数据，同一查询，只换排序方式：

| 查询 | 命中数 | `ORDER BY rank` | `ORDER BY id DESC` | 无排序 |
|---|---|---|---|---|
| DistributedLock | 20,000 | **45.98 / 46.49ms** | **0.30 / 0.43ms** | 0.10ms |
| PlatformId | 20,000 | 30.50 / 32.91ms | 0.25 / 0.34ms | 0.08ms |
| SEIZED | 6,538 | 10.13 / 10.33ms | 0.14 / 0.20ms | 0.05ms |
| 幂等 | 483 | 0.21 / 0.42ms | 0.01 / 0.03ms | 0.01ms |

**结论**：延迟与命中数线性相关，因为 `rank` 必须给每一条命中打 BM25 分。改 `id DESC` 后快 **150 倍**，且对剪贴板场景语义更正确（用户要"最近的"不是"最相关的"）。→ 已列入代码禁令。

### A3 · 多 representation 与压缩

| 项 | 大小 | 相对 plain |
|---|---|---|
| plain 一份 | 837 B | 1.00x |
| plain + html + rtf 三份未压缩 | 2,881 B | **3.44x** ← "1M 变 3M"的真凶 |
| 三份各自 LZFSE 压缩后 | 1,067 B | **1.27x** ← 比只存 plain 一份还小 |

压缩率实测：HTML/RTF → 39.6%；纯中文 → 5.2%；Java 代码 → 4.9%；JSON → 5.8%；**但 120B 短文本 → 97.5%（白费）** → 故设 512B 阈值。压/解耗时均在 0.02ms 量级，可忽略。

### A4 · 加密体积代价

40.63MB 库 ≈ 10,402 pages × 64B 保留区 = **+0.63MB（+1.6%）**。→ 加密**不是**体积问题，代价在延迟。
