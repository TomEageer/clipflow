# Clipflow · 图片 OCR 设计（v0.1）

> 目标：让**截图里的文字可被搜索**（"我截过一张图，里面有那个 IP"）。
> 技术选型：Apple **Vision** 框架，本地运行、零第三方依赖、零成本。
> 本文所有数字为本机实测（M4 Pro / macOS 27 / Swift 6.2.4，2026-08-10），脚本 `bench/ocrbench.swift`、`bench/ocrdiag.swift`。

---

## 1. 实测结论

### 1.1 语言支持

`VNRecognizeTextRequest.supportedRecognitionLanguages()` 返回 **33 种**，含 `zh-Hans` / `zh-Hant` / `yue-Hans` / `yue-Hant` / `ja-JP` / `ko-KR` 等。中文原生支持，无需第三方 OCR。

### 1.2 准确率（字符级 LCS 比对已知原文）

| 场景 | accurate + zh/en | fast + zh/en | accurate + 仅 en |
|---|---|---|---|
| 中文文档 16pt 浅色 | **100.0%** | 44.7% | 30.1% |
| 终端日志 11pt 小字深色 | 94.2% | **96.4%** | **96.7%** |
| IDE 代码 15pt 深色 | 80.0% | 88.0% | **92.0%** |

**关键结论：语言配置不能一刀切。**
- 有中文 → 必须 `["zh-Hans","en-US"]` + `.accurate`，否则掉到 44%/30%
- 纯代码/日志 → 纯英文模型反而**更准**（中文模型会把 `{}` `=` `/` 等符号误判成汉字）
- → 设计上：**先按内容类型/像素特征分流，再选语言配置**；或双跑取置信度高者（代价翻倍，M4 后再评估）

### 1.3 速度

| 项 | 实测 |
|---|---|
| 小图（2800×840 以内）accurate | 30 ~ 250 ms |
| 进程内首次调用 | 204.5 ms，之后稳定 32~51 ms |
| 全屏截图 6912×4468（2x backing）fast | **252 ms / 90 块 / 2454 字** |
| 换语言组合（en / zh / ja / zh+en） | 48 ~ 130 ms，**无显著二次模型加载代价** |

> ⚠️ 首轮测试中曾观测到单次 **15.9 秒**的极端耗时，干净重测无法复现（首次仅 204ms）。推测为系统级 Vision 模型的首次加载/资源准备，**未能定位确切根因**。不作为结论，但足以支撑"OCR 必须异步、绝不能挡在入库路径上"。

## 0. ⚠️ 引擎选型修正：主路径改用 VisionKit `ImageAnalyzer`（Live Text）

> 起因：预览（Preview.app）能直接复制整张截图里的文字，为什么我们直调 Vision 在全屏图上是 0 块？

**先澄清**：预览用的「实况文本 / Live Text」**就是同一个 Vision 引擎**，只是走 `VisionKit.ImageAnalyzer` 这层上层封装。我们一直用的也是苹果自己的 OCR，不存在"换成苹果的"这回事。

**但两层 API 的实际表现不同**（实测）：

| 尺寸 | 宽高比 | `VNRecognizeTextRequest` accurate | `ImageAnalyzer` |
|---|---|---|---|
| 3200×2000（6.4 MP） | 1.6:1 | ✅ | ✅ 2727 字 |
| **4000×2250（9.0 MP）** | 1.8:1 | ❌ **0 块** | ✅ **3036 字** |
| **3600×1500（5.4 MP）** | 2.4:1 | ❌ **0 块** | ✅ **1964 字** |
| 1500×3600（5.4 MP） | 0.4:1 | ✅ | ✅ 4938 字 |
| 4800×2700（13.0 MP） | 1.8:1 | ❌ | ❌ 0 字 |
| 6912×782（5.4 MP） | 8.8:1 | ❌ | ❌ 0 字 |
| 6912×4468（30.9 MP） | 1.5:1 | ❌ | ❌ 0 字 |

**结论**：
1. **`ImageAnalyzer` 安全区更宽** —— 上限约 **9.0 ~ 13.0 MP**（VN accurate 是 6.4 ~ 9.0 MP），长宽比 2.4:1 也能过（VN 不行）。但 8.8:1 极端横长仍失败。
2. **`ImageAnalyzer` 救不了全屏截图** —— 30.9 MP 同样 0 字、`hasResults=false`。
   → **预览能处理全屏截图，是它在 UI 层按可见区域/缩放层级自己做了分块，不是引擎更强。切块这步我们省不掉。**
3. **`ImageAnalyzer` 无 15 秒冷启动** —— 首次 181 ms，之后 131~137 ms；同进程内 VN accurate 首次仍是 13,950 ms。
4. **识别质量略好** —— 1.4 MP 图上 1109 字 vs VN accurate 1076 字 vs VN fast 1012 字，中文标点更准。

**30.9 MP 全屏图三方案实测**：

| 方案 | 字数 | 耗时 |
|---|---|---|
| ImageAnalyzer 直出 | 0 | 76 ms |
| VN accurate 3×2 切块 | 5637 | 17,730 ms（含冷启动） |
| **ImageAnalyzer 3×2 切块** | **6023** | **2,261 ms** |

### 修正后的引擎策略

```
主路径：ImageAnalyzer（安全区 ≤9 MP 且长短边比 < 2.4:1）
  ├─ 超安全区 → 网格切块 + ImageAnalyzer（切法同 §2.2）
  ├─ 仍空     → VNRecognizeTextRequest .fast 兜底（30.9MP 上仍能出 109 块 4313 字）
  └─ 仍空     → no_text
```

**保留 VN 的两个理由**（不能只用 ImageAnalyzer）：
1. **兜底**：VN fast 在 ImageAnalyzer 失败的超大图上仍有产出
2. **`boundingBox`**：修复切块碎片（§2.2a）需要每条结果的几何坐标，而 `ImageAnalyzer` 只给整篇 `transcript`，不暴露逐条边界框 → 走切块路径时可能仍需 VN

**[待验证]**：`ImageAnalyzer` 标注为 `@MainActor`、面向交互式 UI 设计。**后台批量、无窗口环境下长期稳定性未验证**，M4 需压测（连续处理数百张、长时间运行是否有句柄/内存问题）。

## 1.4 性能实测（补测：CPU / 内存 / 吞吐 / 并发）

机器：M4 Pro 12 核 / 24 GB。全部已预热。

### 单张耗时（文字 28px，1x 画布）

| 画布 | 百万像素 | accurate | fast |
|---|---|---|---|
| 1600×900 | 1.4 MP | 407 ms / 98 块 / 920 字 | 87 ms / 36 块 / 905 字 |
| 2400×1350 | 3.2 MP | 591 ms / 136 块 | 128 ms / 54 块 |
| 3200×1800 | 5.8 MP | 790 ms / 169 块 | 176 ms / 72 块 |

**accurate 比 fast 慢约 4.5 倍**，但块数多一倍以上（分行更细）。

### 批量吞吐（30 张 1600×900 串行）

| 模式 | 总耗时 | 单张均 | 吞吐 | CPU 占用 |
|---|---|---|---|---|
| accurate | 13.30 s | 443 ms | **2.3 张/s** | 11.88 s（0.89 核） |
| fast | 3.03 s | 101 ms | **9.9 张/s** | 3.01 s（1.00 核） |

### ⚠️ 并发零收益（重要）

| 并发度 | 总耗时 | 吞吐 | 加速比 | CPU |
|---|---|---|---|---|
| 1 | 12.53 s | 2.4 张/s | 1.00x | 0.93 核 |
| 2 | 12.48 s | 2.4 张/s | 1.00x | 0.95 核 |
| 4 | 12.26 s | 2.4 张/s | 1.02x | 0.95 核 |
| 8 | 12.08 s | 2.5 张/s | **1.04x** | 0.96 核 |

**Vision 内部串行化**（CPU 恒定 ~0.95 核，与并发度无关）。
→ **队列并发度设 1，不要写线程池**：多线程零收益、只增内存。

### 内存：不是泄漏，但超预算

| 对照组 | 连续 10 张 6912×4468 后净增 |
|---|---|
| A：只造图不 OCR | **0.0 MB** ← 图像本身完全不累积 |
| B：造图 + OCR（fast） | **+211.6 MB**（第 5 张 +179 MB → 第 10 张 +212 MB，**增长放缓**） |

结论：Vision 自身约 **+200 MB 并趋于平稳**，是缓存不是泄漏。
> 注：首轮测试曾观测到净增 2.46 GB，系脚本未加 `autoreleasepool` 所致，非真实泄漏。已更正。

**但这撞上了「常驻内存 < 80 MB」的性能预算** → 见 §2.2。

## 2. ⚠️ 最重要的发现：accurate 模式会静默返回空

**现象**：在 6912×4468 的全屏截图上，`.accurate` 模式**返回 0 块 0 字**——不报错、不抛异常、不警告，就是空数组。同一张图 `.fast` 模式正常识别出 **90 块 2454 字**。

### 2.1 已定位：两条硬约束，且互相冲突

用受控实验（1x 画布、固定文字像素高、只变单一变量）夹逼出边界：

**实验 A — 固定文字 28px，只变画布大小**

| 画布 | 百万像素 | accurate | fast |
|---|---|---|---|
| 3200×1800 | 5.8 MP | ✅ 169 块 1856 字 | ✅ 72 块 |
| **4000×2250** | **9.0 MP** | ❌ **0 块**（仅 45ms，未真正识别） | ✅ 90 块 |
| 5600×3150 | 17.6 MP | ❌ 0 块 | ✅ 126 块 |
| 6912×4468 | 30.9 MP | ❌ 0 块 | ❌ **0 块** |

**实验 B — 固定画布 3200×1800，只变文字像素高**

| 文字高 | accurate | fast |
|---|---|---|
| 28 px | ✅ 164 块 | ✅ 70 块 |
| **20 px** | ❌ **0 块** | ✅ 100 块 |
| 14 px | ❌ 0 块 | ✅ 125 块 |
| 10 px | ❌ 0 块 | ❌ 0 块 |

**实验 C — 固定 5.4 MP，只变宽高比**（这组推翻了"面积上限"的解释）

| 尺寸 | 宽高比 | accurate |
|---|---|---|
| 6912×782 | 8.8:1 | ❌ 0 块 |
| 4800×1125 | 4.3:1 | ❌ 0 块 |
| 3600×1500 | 2.4:1 | ❌ 0 块 |
| 2700×2000 | 1.4:1 | ✅ 140 块 |
| 2325×2325 | 1.0:1 | ✅ 137 块 |
| **1500×3600** | **0.4:1** | ✅ **175 块**（同样 5.4MP，竖长就正常） |

**实验 D — 固定高 2000，只变宽**：2000 / 2400 / 2700 / 2800 / 2900 / 3000 / 3200 宽 **全部 ✅**（最高 6.4 MP）。

### 2.1a 结论：给出经验安全区，不宣称根因

单一维度都解释不了——**面积、宽度、长宽比都有反例**：

- 3200×1800（5.8MP）✅ 但 4000×2250（9.0MP，同为 1.78:1）❌ → 不只是长宽比
- 3200×2000（6.4MP）✅ 但 3000×1000（3.0MP）❌ → 不只是面积
- 3600×1500 ❌ 但 1500×3600 ✅（同面积、互为转置）→ 宽高不对称

**根因 [未能确认]**。但可以给出覆盖全部实测点的**经验安全区**：

> **宽高比 < 2:1（长短边之比）且面积 ≤ 6.4 MP → accurate 稳定工作。**
> 全部通过点均落在区内，全部失败点均落在区外。

| 约束 | accurate | fast |
|---|---|---|
| 安全区 | **宽高比 < 2:1 且 ≤ 6.4 MP** | 更宽松，但 30.9 MP 时也观测到过 0 块（不稳定） |
| 文字最小像素高 | 20 ~ 28 px | 10 ~ 14 px |

超限时**静默返回空数组，不报错、不警告**，且耗时骤降（790ms → 29~45ms），说明是提前放弃而非识别失败。

### 2.1b 冷启动：每个新进程首次调用约 15 秒（已复现）

| 场景 | 首次 accurate | 第 2、3 次 |
|---|---|---|
| 全新编译二进制，进程内第一次调用 | **15,336 ms** | 72 ms / 70 ms |
| 另一次全新进程 | 15,250 ms | — |

先前"无法复现"是因为当时进程/系统已被预热。**在冷进程中稳定复现约 15 秒**。

**设计影响（重要）**：这与 §2.3 的 XPC 方案冲突——XPC service 空闲被系统回收后，下次唤醒要再付 15 秒。
→ **必须批处理**：队列积累到一批再唤醒 OCR service 一次性处理完，而不是来一张唤醒一次。15 秒在一批 N 张上摊薄才可接受。
→ OCR 全程在后台、用户不等待，15 秒不影响交互，但**影响耗电**，故批处理是必需而非优化。

### 2.2 关键推论：必须分块（tiling），不能降采样

**两条约束互相冲突**：
- 图超过 5.8 MP → 想让 accurate 工作就得缩小
- 但缩小会让文字像素高等比下降 → 跌破 20~28 px 下限 → 依然是 0 块

**这正是早期"降采样到 50%/25% 仍为 0 块"的原因**——解决了画布约束，制造了文字高度问题。

**正确方案：切成网格，保持文字原始像素高度。**

⚠️ **必须切网格，不能只切横条**。早期原型按高度切成 6912×782 的横条——面积达标但宽高比 8.8:1，落在安全区外，**实跑仍是 0 块**、只能靠 fast 兜底。

切块算法：**每轮切更长的那一边**，自然收敛到近正方形，同时满足面积与宽高比两个约束。

```
输入 6912×4468 (30.9 MP)
  └─ 收敛到 3 列 × 2 行，每块约 2419×2345（5.7 MP，宽高比 1.03），重叠 5%
      └─ 每块独立 accurate OCR（块间串行 —— Vision 并发零收益）
          └─ 按块在原图的 x/y 偏移还原阅读顺序，重叠区去重
```

**实测效果对比**（同一张 6912×4468、文字 30px）：

| 方案 | 结果 |
|---|---|
| accurate 直出 | **0 块 0 字** |
| fast 直出 | 109 块 4313 字 / 371 ms |
| 横条切块（错误做法） | 0 块 → 被迫回退 fast |
| **网格切块 + accurate** | **540 块 / 2126 ms，无需回退** |

若文字本身就 < 20px（高分屏小字截图），accurate 无论怎么切都不行 → 此时才回退 fast（其下限 10~14px）。

**判定顺序**：`安全区内 → accurate 直出` → `超安全区 → 网格切块 accurate` → `仍空 → fast` → `仍空 → no_text`

### 2.2a ⚠️ 已知缺陷（未解决，M4 待办）

网格切块**机制上跑通了**（不再 0 块、不再触发回退），但**文本质量未达标**：

- 手工整块相加得 5637 字，原型走完去重只剩 3077 字
- 首行出现 `40-` 这类**碎片** —— 切割把文字行从中间截断，5% 重叠不足以覆盖
- 按整行字符串去重的策略会把碎片当独立行保留

**修法（M4 实现）**：改用每个 `VNRecognizedTextObservation.boundingBox` 映射回原图坐标做**几何合并** ——
边界框贴住切块边缘的判定为被截断片段，与相邻块的对应片段拼接或丢弃，而不是按字符串去重。

### 2.3 ⚠️ 修正 D2：OCR 必须放独立 XPC 进程

原 [00 §7 D2](./00-架构设计.md) 决定"单进程 + actor 隔离，不拆 daemon"。**实测数据推翻了这条在 OCR 场景下的适用性**：

- 性能预算承诺**常驻内存 < 80 MB**
- 实测 OCR 使进程内存 **+200 MB 并驻留不还**（缓存性质，趋稳但不回落）

→ **OCR 单独拆成 XPC service**（`ClipflowOCRService`）。理由：
- XPC service 空闲时由系统自动终止回收，主进程常驻内存不受污染
- OCR 崩溃（超大图/畸形图）不会拖垮主进程
- 只为 OCR 一个用途拆，复杂度可控；其余模块仍遵守 D2 单进程

> 这是新证据推翻既有决策的情形，D2 需在 00 文档标注例外。

### 2.4 静默失效的硬防线

这是"代码在跑、测试也过、生产上什么都没索引"的典型形态，必须防：

| 防线 | 做法 |
|---|---|
| **双模式回退** | `.accurate` 返回空 → 自动 `.fast` 重试 → 仍空才标记 `no_text`。**不允许一次空就当没文字** |
| **启动自检 canary** | 内置一张已知文字内容的图，每次启动跑一遍 OCR 校验引擎确实工作；识别不出立即告警并记日志 |
| **可观测** | 记录 OCR 成功率/空结果率指标，空结果率异常升高要能被发现 |

> 绝不接受"调用了就当它生效了"。

## 3. 架构

```
Ingest 管道 ──► 图片正常入库（立即返回，不等 OCR，不阻塞用户）
                    │
                    └─► INSERT INTO ocr_queue（持久化，进程被杀任务不丢）
                                  │
                    OCRWorker（独立 actor · QoS .utility · 低优先级）
                                  ├─ CAS contentHash 查重：同一张图只 OCR 一次
                                  ├─ 跳过 < 100×100（图标/表情，无文字）
                                  ├─ Vision 识别（accurate → 空则 fast 回退）
                                  ├─ 失败重试上限 3 次，超限标记 abandoned
                                  └─► 写 clipflow-index.sqlite：items_ocr + FTS
```

**持久化队列**这一条抄自 Paste（其 `index.sqlite` 里有 `ocr_queue` / `fts_queue` 两张队列表 + `items_ocr` 结果表）——OCR 是秒级任务，进程重启不能丢。

### 3.1 必须做对的细节

| 项 | 做法 | 理由 |
|---|---|---|
| OCR 文本**单独字段** | 存 `items_ocr.text`，不并入原始内容字段 | OCR 有 4%~20% 错误率，混入会污染原始数据的保真性 |
| 搜索结果**标明来源** | 命中 OCR 文本时 UI 标"文字来自图片" | 用户需要知道这条可能有识别误差 |
| **电池感知** | `ProcessInfo.processInfo.isLowPowerModeEnabled` 或电池供电时暂停队列，插电续跑 | OCR 是本项目最耗电的操作 |
| **不重复 OCR** | 按 blob 的 SHA-256 去重 | 同一张图复制 100 次只 OCR 一次 |
| 队列**限流** | 同时最多 1~2 个 OCR 任务 | 避免抢占前台交互的 CPU |

## 4. ⚠️ OCR 与加密设计的冲突（必须配套解决）

**问题**：
> 你截了一张后台登录页的图。原本密码只是一堆像素，躺在**已加密**的 blob 里。
> OCR 一跑，它变成索引库里的**明文可搜索字符串**——而按 [01 §5](./01-存储分级与规模.md) 的设计，**索引库为了搜索速度是不加密的**。

**即 OCR 会绕过整个加密分级设计。** 这不是不能做，是必须配套：

| 方案 | 做法 |
|---|---|
| **A · 敏感识别拦截**（必做） | OCR 结果过正则/邻近词检测（`password` / `密码` / `token` / `secret` / JWT 特征 / 掩码字符 `••••`）→ 命中则**不入索引**，只在 `items_ocr` 里加密存储 |
| **B · OCR 结果继承条目分级** | 若原图被判为敏感 → OCR 文本走敏感路径（加密 + TTL），不进 FTS |
| **C · 用户可关** | 提供"不 OCR 图片"总开关，以及按来源 App 排除（如密码管理器、银行 App 的截图不 OCR） |

**若主库最终采用全库加密（D4 的 M2 闸门通过），本冲突自动消解**——那时索引库也加密，OCR 文本不再是明文落盘。所以 §4 的 A 方案是"主库不加密"情形下的必要补丁。

## 5. 排期与判据
